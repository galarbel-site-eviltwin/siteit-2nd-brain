## 1. ארכיטקטורה

```
                    ┌──────────────────────────────────────────────┐
  דפדפן / נייד ───► │  Next.js על Vercel (fra1)                     │
  בוט WhatsApp ───► │                                              │
                    │  UI ─ שאל את המוח ─ לקוחות ─ קליטה ─ ניהול    │
                    │        │                                     │
                    │        ▼                                     │
                    │  Brain Agent (AI SDK, כלים מוגדרים)           │
                    │   ├─ חיפוש היברידי במקורות                    │
                    │   ├─ שאילתות מובנות (החלטות, הצעות, מחירים)   │
                    │   ├─ בדיקה חיה במקור (Asana/Monday/יומן)       │
                    │   └─ הצעת פעולה  ──►  ממתין לאישור עובד       │
                    │                                              │
                    │  Workflows: קליטה ─ חילוץ ─ שיוך ─ אינדוקס    │
                    └───────┬───────────────────────┬──────────────┘
                            ▼                       ▼
            Supabase (eu-central-1)          שירותים חיצוניים
            Postgres + pgvector              Google (Gmail, Calendar, Drive)
            Storage (פרטי)                   Microsoft Graph (Outlook, יומן)
                                             Asana, Monday, Timeless API
                                             AI Gateway ─► Claude + embeddings
```

שלושה עקרונות מבניים:

1. **המודל לא מבצע פעולות.** הוא יכול רק *להציע* פעולה. השרת שומר את ההצעה, מציג תצוגה מקדימה, ומבצע רק אחרי לחיצה של עובד. כך תוכן שנקלט (מייל, תמלול) לא יכול להפעיל פעולה גם אם יש בו הוראה.
2. **כל טענה נשענת על קטע מקור.** התשובה נבנית מקטעים (chunks) עם מזהים, והממשק מציג את הקטע עצמו, לא רק את המסמך.
3. **מערכות המקור נשארות סמכותיות.** סטטוס משימה נבדק ב-Asana/Monday בזמן אמת; המוח שומר רק תמונת מצב עם חותמת זמן.

## 2. התחברות והרשאות

### התחברות
- Auth.js, ספק Google בלבד. **מי נכנס נקבע לפי רשימת מיילים מאושרים**: השרת בודק שהמייל נמצא בטבלת `employees` עם `active = true`. כל מייל אחר נחסם, גם אם הוא חשבון Google תקין.
- **שלבים 0 עד 4: אפליקציית OAuth חיצונית (External)** בפרויקט Google Cloud של גל. להתחברות בלבד (שם, מייל, תמונה) Google לא דורשת אימות, ולכן לא צריך את אדמין ה-Workspace.
- **משלב 5 (Gmail): אפליקציה פנימית (Internal) של ה-Workspace**, שדני יוצר או מאשר. הסיבה: Google מגדירה קריאת Gmail כהרשאה "restricted". באפליקציה חיצונית זה אומר בדיקת אבטחה חיצונית בתשלום, או חיבור מחדש כל 7 ימים במצב בדיקה. באפליקציה פנימית של הארגון אין צורך באף אחד מהם.
- עזיבת עובד: `active = false` חוסם כניסה מיד, מבטל את הטוקנים שלו למקורות, ומשאיר את הידע העסקי שנקלט.

### רמות הרשאה (גרסה 1)
| תפקיד | מה רואה |
|---|---|
| `member` | כל הידע המשותף של החברה + האזור האישי שלו |
| `admin` (דני) | הכול, כולל אזורים אישיים של כולם. מאשר נהלים |
| אחראי לקוח | תפקיד לכל לקוח (`clients.owner_id`), לא רמת גישה. מאשר החלטות ומתקן מידע ברמת הלקוח |

- כל שאילתה עוברת דרך שכבת גישה אחת (`lib/access.ts`) שמוסיפה את תנאי הנראות. מעליה, RLS ב-Postgres כהגנה שנייה על טבלאות האזור האישי.
- המבנה תומך מראש בהרשאה לפי לקוח או סוג מידע (עמודת `visibility` על פריטים), אבל בגרסה 1 הערך תמיד `company` או `personal`.

|---|---|

| `client_aliases` | client_id, kind (`name`/`domain`/`email_domain`/`nickname`), value. משמש לשיוך אוטומטי |

### מקורות וקליטה
| טבלה | שדות עיקריים |
|---|---|
| `connections` | id, provider (`google`/`microsoft`/`asana`/`monday`/`timeless`/`whatsapp`), owner_id, scope, status, last_success_at, last_error |
| `items` | id, kind (`meeting`/`email_thread`/`chat`/`document`/`voice_note`/`note`), title, source_connection_id, external_id, **occurred_at**, **recorded_at**, created_by, visibility, client_id?, project_id?, assignment_status (`suggested`/`confirmed`/`none`), storage_path, content_hash, ingest_status |

`content_hash` מזהה כפילויות (אותו תמלול שהועלה פעמיים, אותה פגישה בשני יומנים). כפילות מסומנת ומקושרת, לא נמחקת.

`explicit` (נאמר במפורש) · `employee_report` (דיווח עובד) · `client_statement` (אמירת לקוח) · `ai_inference` (הסקת AI) · `unknown`.

| טבלה | שדות עיקריים |
|---|---|
| `decisions` | id, client_id, project_id?, text, **state** (`idea`/`request`/`agreed_in_principle`/`approved`/`cancelled`/`superseded`), supersedes_id?, approved_by?, reason?, alternatives?, occurred_at, evidence_type |
| `commitments` | id, client_id, text, owner (employee/contact/unknown), due_at?, due_raw ("בחמישי"), status, linked_task_ref? |
| `proposals` | id, client_id, project_id?, title |
| `proposal_versions` | id, proposal_id, version, sent_at, **price**, currency, scope, outcome (`pending`/`accepted`/`rejected`/`revised`), item_id (המסמך) |
| `preferences` | id, client_id, scope (`client`/`project`/`campaign`), kind (`tone`/`message`/`constraint`/`rejected`), text |
| `procedures` | id, title, body, owner_id, status (`draft`/`approved`/`deprecated`), reviewed_at |
| `evidence` | id, record_type, record_id, chunk_id, quote |
| `corrections` | id, record_type, record_id, field, old_value, new_value, by, reason, at |

### שיחה ופעולות
| טבלה | שדות עיקריים |
|---|---|
| `conversations` | id, employee_id, scope (`company`/`client`/`project`/`sources`), scope_ref |
| `messages` | id, conversation_id, role, content, citations (chunk_ids), evidence_labels |
| `actions` | id, proposed_in_message_id, kind (`create_task`/`send_email`/`send_message`/`create_event`), target, payload, **status** (`proposed`/`approved`/`executed`/`failed`/`rejected`), approved_by, executed_at, result |

### זמן כחלק מהידע
לכל פריט שני זמנים: `occurred_at` (מתי זה קרה) ו-`recorded_at` (מתי המוח ידע על זה). שאלה כמו "מה ידענו כששלחנו את ההצעה?" מסננת לפי `recorded_at <= T`. בזכות זה הודעה מאוחרת לא מיוחסת למשתתפי פגישה קודמת.

## 4. קליטת מידע

### מסלול משותף (Workflow)
```
העלאה / ייבוא ─► שמירה ב-Storage ─► חילוץ טקסט ─► [תמלול אם צריך]
   ─► פירוק לקטעים ─► embeddings ─► הצעת שיוך (לקוח, פרויקט, משתתפים, תאריך)
   ─► חילוץ ידע (החלטות, התחייבויות, הצעות, מחירים) ─► ממתין לאישור / נקלט
```
- כל צעד נשמר ב-`ingest_jobs`; כשל מאפשר ניסיון חוזר מאותו צעד, והממשק מראה מה כן נקלט.
- **שיוך:** קודם התאמה דטרמיניסטית (דומיין מייל, שם מתוך `client_aliases`), ורק אחר כך הצעה של המודל. הצעה של המודל תמיד `suggested`, לעולם לא `confirmed` אוטומטית.
- **חילוץ ידע:** מודל מהיר (Haiku) מחזיר JSON לפי סכמה, כשכל רשומה מצביעה לקטעים. פריטים מהותיים (מחיר, אישור, תאריך יעד) נכנסים לתור "לבדיקה" אם סוג הראיה אינו `explicit`.
- **תאריכים יחסיים:** "בחמישי" מפוענח לפי `occurred_at` של הפריט, לא לפי יום ההעלאה, ונשמר גם בצורתו המקורית.

### מקורות
| מקור | גרסה 1 | בהמשך |
|---|---|---|
| **Timeless** | העלאה ידנית של תמלול (TXT/DOCX/PDF מהייצוא) או הדבקה. מפענח דוברים וחותמות זמן כשהם קיימים | כפתור "ייבא מ-Timeless": רשימת פגישות מה-API, העובד בוחר אילו נכנסות. עדיין לא אוטומטי. דורש חבילת Pro ומעלה |
| **WhatsApp** | העלאת ייצוא צ'אט (`.txt` או `.zip` עם מדיה). מפענח את הפורמט של ייצוא WhatsApp בעברית ובאנגלית, מתמלל הודעות קוליות | בוט: forward של הודעה או הקלטה נקלט ישר |
| **מסמכים** | PDF, DOCX, XLSX, PPTX, TXT, MD, תמונות וצילומי מסך (חילוץ טקסט בעזרת מודל ראייה) | Google Drive / OneDrive לפי תיקייה |
| **הקלטה קולית** | הקלטה בדפדפן או העלאת קובץ, תמלול, סימון שמות/מספרים לא ודאיים | |
| **Gmail + Google Calendar** | שלב ה' (ראה §10). רק שרשורים שמשויכים ללקוח לפי דומיין או כתובת | |
| **Outlook + יומן Microsoft** | שלב ו'. Microsoft Graph, הרשאה delegated לכל עובד, אותו סינון | |
| **Asana + Monday** | שלב ז'. קריאה חיה של סטטוס + יצירת משימה באישור | |
| **Crawler + AI CMS** | | ממצאי סריקה ותוכן שפורסם, מקושרים ל-`sites` |

**סינון מייל:** המוח לא קולט את כל תיבת הדואר. רק שרשורים שבהם משתתף מישהו מדומיין של לקוח (או כתובת של איש קשר). זה מקטין עלות, רעש וחשיפה של מייל אישי.

## 5. "שאל את המוח"

### זרימה
1. **קביעת היקף:** חברה, לקוח, פרויקט או אוסף מקורות. תמיד גלוי בממשק. מעבר ללקוח אחר מעדכן את ההיקף במפורש.
2. **הסוכן** (Claude Sonnet דרך AI Gateway) מקבל את השאלה, את ההיקף ואת היסטוריית השיחה, ויש לו כלים:

| כלי | מה עושה |
|---|---|
| `search_sources` | חיפוש היברידי: וקטורי (`pgvector`) + טקסטואלי (`pg_trgm`, כי ל-Postgres אין מילון עברית), איחוד בשיטת RRF, סינון לפי היקף, זמן ו-`recorded_at` |
| `list_meetings` | רצף פגישות של לקוח לפי תאריך. זה מה שמאפשר לפענח "לפני שתי פגישות" |
| `get_client_state` | סקירה, החלטות תקפות, התחייבויות פתוחות, חסמים |
| `get_decisions` / `get_commitments` | עם מצב, מקור וסוג ראיה |
| `get_proposals` | גרסאות, מחירים, תוצאה. בסיס ל"היסטוריית מחירים" |
| `query_portfolio` | שאלות רוחביות על כל הלקוחות ("עם מי לא דיברנו חודש?", "כמה גבינו על אתר תדמית?"). מריץ שאילתות מוגדרות מראש, לא SQL חופשי |
| `live_check` | סטטוס עדכני ב-Asana / Monday / יומן |
| `propose_action` | יוצר רשומת `actions` בסטטוס `proposed`. לא מבצע |
| `ask_clarification` | כשיש כמה פירושים שמשנים את התשובה (למשל שתי פגישות מועמדות) |

3. **פורמט התשובה:** מענה ישיר, הסבר, מקורות, הסתייגות אם יש, הצעת המשך. כל משפט מהותי נושא מזהה קטע, והממשק ממיר אותו לציטוט שנפתח בצד (קטע תמלול עם חותמת זמן, פסקה במסמך). סוג הראיה מוצג במילים ("נאמר במפורש", "דיווח של מנהל הלקוח", "פרשנות"), בלי אחוזים.
4. **בדיקת ביסוס:** לפני שהתשובה מוצגת, בדיקה אוטומטית שכל ציטוט מצביע לקטע שקיים ושנמצא בהיקף ההרשאה. טענה בלי קטע תומך מסומנת כפרשנות או מוסרת.
5. **מצב "מקורות בלבד":** אותו חיפוש בלי תשובת AI, לפי האפיון.

### תדריך לפגישה
שאילתה מובנית מעל אותם כלים: סיכום הפגישה האחרונה, החלטות תקפות, התחייבויות פתוחות, הצעה אחרונה, שאלות פתוחות, וחוסרים ("אין תמלול לפגישה מ-12.9"). ההכנה נפתחת מהיומן ב"היום שלי".

## 6. פעולות באישור

```
הסוכן מציע ─► actions.status = proposed ─► תצוגה מקדימה מלאה (נמען, נושא, גוף / פרטי משימה)
   ─► העובד עורך ומאשר ─► approved ─► השרת מבצע עם הטוקן של העובד ─► executed / failed
```
- הביצוע תמיד עם החשבון של העובד המאשר (המייל שלו, ה-Asana שלו), כך שמבחינת הלקוח זו הודעה רגילה מהעובד.
- הודעה ללקוח מקבלת תצוגה מקדימה עם אזהרה אם היא מכילה משהו שסומן כפנימי (מחירי עלות, הערות אישיות).
- כל פעולה נשמרת עם התוצאה שלה. כשל מוצג כשל, לא כהצלחה.
- אין פעולות בכמות (שליחה לכמה לקוחות בבת אחת) בגרסה 1.

## 7. בוט ושאלה קולית

- **בוט WhatsApp** על מספר עסקי ייעודי (WhatsApp Cloud API של Meta). אותו בוט משמש לשני דברים: forward של תוכן לקליטה, ושאלות. זיהוי העובד לפי מספר הטלפון שלו ב-`employees`. מספר לא מוכר לא מקבל שום מידע.
- החלופה הזולה והמהירה להקמה היא Telegram, בלי אימות עסקי של Meta. אם אימות ה-Business של Meta יתעכב, אפשר להתחיל ב-Telegram ולעבור.
- **שאלה קולית:** הקלטה ← תמלול ← אותו סוכן ← תשובה בטקסט. תשובה מוקראת (TTS) אופציונלית, למצב נהיגה.
- בערוץ הבוט אין אישור פעולות בגרסה 1: הבוט יכול להציע פעולה ולשלוח קישור לאישור בממשק.

## 8. אבטחה

- **הזרקת הוראות:** תוכן שנקלט מסומן כנתון בתוך ההנחיה למודל, ולכלים עם תוצאה חיצונית אין מסלול ביצוע בלי אדם (§6). זו ההגנה העיקרית, לא ניסוח ההנחיה.
- **סודות:** טוקני OAuth מוצפנים במסד (הצפנה בצד האפליקציה, מפתח במשתני סביבה של Vercel). בחילוץ, מחרוזות שנראות כמו סיסמה או מפתח API מוסוות ולא נכנסות לאינדקס.
- **קבצים:** הדלי פרטי; הורדה רק דרך קישור חתום קצר-מועד שהשרת מנפיק אחרי בדיקת הרשאה.
- **יומן ביקורת:** כניסות, צפייה באזורים אישיים (גם של דני, שקוף לעובדים), תיקונים, פעולות.
- **גיבוי:** גיבוי יומי של Supabase (כלול ב-Pro) + ייצוא שבועי של הטבלאות המובנות.

## 12. לגבי מעבר עתידי ל-Firebase

המבנה כאן רלציוני בעומק: החלטות שמחליפות החלטות, גרסאות הצעה, שאילתות רוחביות על כל הלקוחות, וחיפוש וקטורי יחד עם סינון. Firestore יכול לעשות חיפוש וקטורי, אבל שאילתות רוחביות וצירופים יהיו שם מסובכים ויקרים יותר. **ההמלצה: להכריע לפני שלב 3.** אחרי שלב 3 המעבר הוא כתיבה מחדש של שכבת הנתונים. כדי להשאיר את הדלת פתוחה, כל הגישה למסד עוברת דרך שכבת repository אחת (`lib/db/*`) ולא פזורה בקומפוננטות.
